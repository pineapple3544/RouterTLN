# Berlin 장애물 통로 진입과 3랩 검증

Berlin 정방향에서 각 배치를 처음 보는 상태로 시작했다. 기존에 남은 7건의 실패를 분석한 뒤 C++ 통로 탐색기만 변경했다. 평가 전에 새 장애물 배치 300개를 추첨하고, 최종 후보를 고정한 뒤 같은 배치에서 변경 전후 평가기를 각각 실행했다.

신규 300회에서 기본 버전의 3랩 완주는 293회, 후보는 290회였다. 기본 실행은 기존 탐색기를 유지한다. 후보 C++ 변경 전체와 실제 평가에 사용한 배치·재현 방법은 아래에 남겼다.

`no_corridor` 6건 중 5건은 실제 장애물 근처의 관측 셀만 남겨도 경로가 다시 열리지 않았다. 첫 랩 397361058에서는 안쪽으로 꺾는 조향이 짧은 예측 구간의 여유 기준을 침범한 반면, 바깥으로 향하는 조향은 장애물 출구에 이르기 전에 예측이 끝났다. 지도 셀, 후보 행 비트마스크와 직전 명령은 [diagnostics.json](diagnostics.json)에 저장했다. 파일의 `audit` 배열 순서는 전체 관측, 실제 장애물 근처 관측만 유지, 정적 지도만 유지다. 정확한 장애물 위치는 원인 분리를 위한 사후 재생에만 사용했다.

## 탐색기 변경

- 장애물 메모리에서 실제로 관측한 좌우 위치와 커브 방향을 함께 본다. 통로 쪽이 확인되면 필요한 횡이동과 주행 곡률로 조향 시작 거리를 정한다.
- 급커브에서 기본 조향의 예상 차체가 여유 영역을 침범하면, 장애물 출구 뒤까지 두 가지 후속 조향을 비교한다. 일반 탐색이 모두 실패하면 현재 차체 방향에서 시작하는 곡선을 추가로 만들고 차체가 지나가는 구간을 검사한다.
- 둘째 랩부터 첫 랩에서 실제로 지난 궤적이 현재 열린 통로 안에 있는지 확인한다. 연속 장애물에서 반대편 통로로 넘어가야 하면 첫 통로의 열린 범위 안에서 다음 진입 방향을 고려한다.

주행 입력은 LiDAR와 Berlin 정적 지도에 기반한 위치 추정이다. 배치별 정답 좌표, 시드, 웨이포인트 상수는 위 제어 변경에 쓰지 않았다. Race 상한은 3.5m/s, 계획 주행에서 원본 Avoid의 속도 범위는 2.7–3.0m/s, Race 제동 예측은 0.18초다. 첫 랩 탐색 속도는 별도다. 150ms 센서 보호와 25ms 제어 시간 보호를 유지했다.

## 평가 방법

기존 300개는 장애물 3개 배치다. 새 300개는 장애물이 1개, 3개, 5개인 배치를 각 100개씩 추첨했다. 폭 0.30m의 장애물을 한 주행의 세 랩 동안 고정하고, 매 배치에서 계획을 초기화했다. 두 버전의 배치와 센서 노이즈 시드는 일치한다. 시뮬레이터는 10ms 간격, 오프라인 제어기는 20ms와 30ms를 번갈아 사용한다. 3랩 통과는 3랩 완주, 접촉 0, 안전 거부 0, 출발 0.5m 이후 최저속도 0.05m/s 이상을 모두 요구한다. 첫 랩 수는 실제 첫 결승선 통과 횟수다. 이는 대회의 180초 또는 최대 10랩 평가와 별도의 검증이다.

## 랩타임 개선 순서

1. **첫 랩과 연속 통로 제약을 먼저 확인한다.** 이전에 통과했던 4개 저속 첫 랩 제동 거부의 직전 상태에서 두 탐색기의 후보 궤적을 재생한다. 출구까지의 조향 비용에 차체 전체의 최소 제동 여유를 반영하고 기존 보호 판정은 유지하는 방안을 시험한다. 489928091에서 첫 통로 진입 전 자세를 복원해 초기 방향·횡위치·조향 적용 지연을 바꾼다. 다음 통로까지 연속으로 차체가 지나갈 수 있는 경로를 찾고, 2.7m/s에서 가능한 횡이동과 실측 조향 지연을 비교한다. 새 300개는 이후 개발에 사용하면 다음 독립 검증에서 제외한다.
2. **속도가 실제 상한에 닿은 직선부터 시험한다.** 첫 랩과 Avoid 속도 범위를 유지하고, 계획을 만든 뒤 Race 직선의 상한만 3.5 → 3.65 → 3.75m/s로 올린다. 현재 스캔에서 제동 거리와 출구 여유가 모두 확보될 때만 가속한다. 장애물이 잦은 배치는 회피 후 복귀할 때 재가속이 늦는 구간을 따로 계측한다. 두 변경은 각각 시험한다. ROS 681276235에서 상한 근처였던 4.97초 동안 같은 거리를 즉시 3.65m/s로 달린다고 단순 계산하면 약 0.20초가 줄어든다. 가속에 걸리는 시간과 다음 제동 시점은 실험에서 측정한다.
3. **속도 채택 기준을 분리한다.** 같은 배치에서 기존 완주 손실·새 첫 랩 실패·충돌·25ms 제어 초과가 없고 공통 완주의 베스트랩이 줄어드는 후보를 고른다. 새로 봉인한 배치에서도 확인한 뒤 ROS에서 장애물 1·3·5개를 동일 설정으로 180초 또는 10랩까지 평가한다. 연속 완주 수와 베스트랩을 함께 비교하고, 10m/s는 설계 한계로만 사용한다.

## 재현

RouterTLN 루트를 컨테이너의 `/workspace`에 마운트하고 기존 Gym 및 ROS 환경을 사용한다. [배치 파일](random-300.json)의 추첨 시드는 `159590893218`이다. [freeze.json](freeze.json)에 평가 전 고정한 배치, 헤더와 실행 파일의 SHA-256을 기록했다. [passage.patch](passage.patch)는 이 실험이 변경한 전체 소스 차이다. 기본 소스에는 변경 전 탐색기가 들어 있다. 후보를 소스에서 재현할 때는 프로젝트의 **별도 사본**에서 `git apply --check experiments/berlin-passage/passage.patch`와 `git apply experiments/berlin-passage/passage.patch`를 순서대로 실행하고 그 사본을 빌드한다. 로컬 실험 컨테이너에서는 빌드 없이 `EL_EVAL_BINARY=/workspace/runs/berlin-corridor-recovery/final-evaluator`로 고정 후보를 선택할 수도 있다. 변경 전 헤더의 SHA-256은 `e746e0a89a87ff070fc22ff8ae1e0ae2989c9d98fd1d33a1a735a6b9bc181087`다.

```bash
cd /workspace
source /opt/ros/humble/setup.bash
source /home/misys/forza_ws/race_stack/install/setup.bash
export PYTHONPATH="/home/misys/forza_ws/race_stack/base_system/f110_simulator/f1tenth_gym/gym:${PYTHONPATH:-}"
export OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1
cmake --build /build --target el_eval_avoid el_controller
export EL_EVAL_BINARY=/build/el_eval_avoid EVAL_CORES=0,2,4,6
python3 experiments/berlin-passage/verify.py seven after
python3 experiments/berlin-passage/verify.py known after
python3 experiments/berlin-passage/verify.py fresh after
```

변경 전 평가기에도 같은 세 명령을 적용한다. `EL_EVAL_BINARY`를 해당 실행 파일로 바꾸고 결과 이름 `after`는 `before`로 바꾼다. 평가기는 각 이름에 새 디렉터리를 만들므로 다시 돌릴 때는 새 이름을 지정한다. [paired.csv](paired.csv)에 600개 배치의 전후 판정과 각 랩타임, [results.json](results.json)에 실패 목록, 비교 통계와 모델 해시, [ros-layouts.json](ros-layouts.json)과 [ros-results.json](ros-results.json)에 ROS 배치와 개별 판정을 기록했다. 실행 당시 원시 JSONL과 ROS 제어·독립 판정 로그는 로컬 `el-project/native/runs/berlin-corridor-recovery/` 아래에 있다.
