# Berlin 정방향 장애물 진입 조향 검증

39204의 기존 실패는 누적 116.119 m에서 발생했다. 진입 상태를 그대로 복원하면 기존 탐색기는 장애물 오른쪽으로 향하다가 왼쪽 후보로 바뀌었고, 이후 6단계에서 도달 가능한 후보를 모두 잃었다. 수정한 탐색기는 스캔으로 기억한 장애물의 진입부터 출구 너머까지 발자국이 들어가는 횡방향 구간을 찾는다. 장애물 구간의 좌우를 같은 2.5 cm 격자로 비교하고, 탐색 단계 사이의 중간 웨이포인트에서도 차량 점유 영역을 확인한다. 시드 번호나 장애물 정답 좌표는 제어기에 전달하지 않는다.

동일 상태의 2199번째 제어 시점에 장애물까지의 예상 거리는 2.6 m, 통로 중심은 기준선 오른쪽 0.375 m였다. 2211번째 시점(누적 114.676 m)에서 조향 명령은 기존 −0.035 rad에서 수정 후 −0.094 rad로 바뀌었다. 두 경우 모두 목표 속도는 2.7 m/s였다.

## 오프라인 분기

3랩째 누적 113.813 m의 원본 스냅샷(step 2198)을 복원했다. 횡위치 5개(−6, −3, 0, +3, +6 cm), 자세각 5개(−6, −3, 0, +3, +6°), 속도 변화 3개(−0.15, 0, +0.15 m/s)를 조합했다. 수정 전에는 52/75개가 결승선에 도달했고 23개가 no_corridor로 정지했다. 수정 후에는 75/75개가 결승선에 도달했고 안전 거부와 충돌이 모두 0건이었다. 각 분기는 복원 시점부터 3랩 결승선까지 계산했다.

원본 스냅샷 및 모델 SHA-256은 [results.json](results.json)에 있다. [분기별 결과](paired-v3/outcomes.csv), [기존 기준 분기](diagnostic/unchanged.jsonl), [수정 후 기준 분기](paired-v3/unchanged.jsonl), [CTest 8종](test-v3.log).

## ROS 2 Humble 시뮬레이션

Berlin 정방향, 시작 웨이포인트 37, 장애물 3개. WSP Race와 원본 Avoid를 사용했다. 계획 주행의 Avoid 목표 속도 범위는 2.7–3.0 m/s, 센서 보호 기준은 150 ms다. 시드마다 별도 프로세스로 두 번 출발했고, 모든 출발에서 계획 준비 상태, 계획 전환 수, 계획 감속 수가 0임을 확인했다. 첫 랩의 주행에서 계획을 만들고 2·3랩에서 계획 감속이 실행되는지 확인했다. 실제 장애물 위치와 방향도 ROS가 발행한 값과 대조했다.

## 재현 방법

기존 프로젝트 Docker 컨테이너 el-native-dev의 /workspace에서 실행한다. /build는 이 소스에 대해 구성된 Release 빌드 디렉터리다. 각 명령의 출력 디렉터리는 새 경로를 사용한다. branches.py는 이전 실행 파일을 해시 검증에 쓰고 복원 후 제어에는 새 실행 파일을 사용한다.

```bash
source /opt/ros/humble/setup.bash
cmake --build /build -j2
ctest --test-dir /build --output-on-failure
python3 runs/berlin-entry-preview/branches.py runs/39204-paired-repeat
python3 runs/berlin-entry-preview/ros.py runs/39204-ros-repeat --spread-cores
```

보관된 캠페인은 ros-a(39204, 39401, 39402)와 ros-b(39403, 39404) 두 그룹으로 CPU와 ROS 도메인을 분리해 실행했다. 보관된 원시 로그를 다시 검사하려면 같은 컨테이너에서 `python3 runs/berlin-entry-preview/audit.py`를 실행한다.
